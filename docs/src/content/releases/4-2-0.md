An application building two shells against 4.0.1 sent back eleven findings in one batch. Nine were ours. Every one was reachable in the first hour of using the library, none was subtle, and the suite — 4,694 tests at the time, with a mutation run behind it — caught none of them.

That is the release. The fixes are small; what they have in common is worth more than any of them.

### A Closed Menu Put A Scrollbar On The Page

The worst symptom-to-cause distance in the batch: a horizontal scrollbar appears and nothing is visibly off-screen.

`arc-dropdown-menu` hid its resting panel with `opacity: 0; visibility: hidden`, so the open transition had two states to animate between. A `visibility: hidden` box still takes part in layout and still contributes scrollable overflow, and the panel is `position: absolute; inset-inline-start: 0; min-width: 200px`. Anchored to a trigger at the right edge of a full-width row — a table's row-action menu, which is the canonical placement — the closed panel hung 200px past the document edge. Measured in the reporting application at a 1680px viewport: `scrollWidth` 1800 against a `clientWidth` of 1680.

The closed panel is now `display: none`, with `transition-behavior: allow-discrete` and `@starting-style` so both the open and the close transitions survive. That pairing is not new here: the *managed* panels have carried it since they moved to the top layer, for exactly this reason, in the same stylesheet. What was missing was the resting half.

Two siblings were flagged as unmeasured in the report. They are measured now, by a sweep that mounts every overlay **closed** and asserts the document does not scroll: **`arc-popover` 59px, `arc-hover-card` 61px** of page overflow, both fixed the same way. `arc-toolbar`'s panel is `inset-inline-end: 0` and so overflows leftward — no scrollbar in LTR, an RTL case only — and is fixed with the others rather than left as a known-quiet instance. `arc-navigation-menu` measured clean.

### Two Components That Ship Together, Broken When Composed

**`arc-top-bar` never got `fixed` inside `arc-app-shell`.** The shell's body reserves `--nav-height` of padding for a bar it assumes is out of flow, and nothing put it there. So the default composition rendered 64px of bar in normal flow *plus* 64px of reserved padding: a **128px gap at the top of every page**, with no error and nothing in the console. `arc-top-bar`'s own JSDoc has always described the behaviour that was missing — *"Automatically applied when TopBar is placed inside an AppShell"* — which is what made it a defect rather than a gotcha. The shell now applies it.

**The shell flattened the sidebar it is documented to compose with.** Its `::slotted(arc-sidebar)` block forces `height: auto`, correctly, since the shell's own rail owns sticky and height — but that left the sidebar host at content height, and the rail's divider stopped at the last link on a tall page. Measured by the reporter at a 950px viewport: wrapper 886px, host 329px.

The fix is on the box rather than on the tag: the rail is now a grid, so **anything** slotted into it is stretched to full height — `arc-sidebar`, or the plain `<nav>` a consumer reaches for first. `arc-sidebar` no longer relies on a percentage that needs a definite parent, and the dead `min-height` is deleted rather than left in as backup.

### The Shell Can Be Embedded

Found while checking the fix above, and the largest new thing here. `arc-app-shell` could only ever be a full-page layout: `100vh`, page-scrolled, sticky rail. Inside any bounded box — a card, a dashboard cell, a split pane, its own documentation preview — it overflowed rather than fitting.

**`embedded`** is the same layout sized by its container:

```html
<div style="height: 400px">
  <arc-app-shell embedded style="height: 100%"> … </arc-app-shell>
</div>
```

It fills the box, its content area becomes the scroll context instead of the page, the rail is stretched by the body rather than sized from the screen, and the top bar goes back in flow — a fixed bar leaves the container entirely and pins itself to the top of the *screen*, which is a bar floating over the page from a component inside a card. Turning the mode off restores all four.

This began as a `--shell-height` token and was reverted before it shipped: with a sidebar present, the rail's own viewport height forced the shell past any smaller box whatever the host declared, so the token would have been honoured everywhere except the case it existed for. Silently ignoring a dimension someone set is the same mistake as the next item.

### Props And Docs That Described Something Else

- **`arc-sidebar.width` did nothing.** Declared, defaulted to `'280px'` in the constructor, and read by no rule, no `styleMap`, no selector. The 280px a consumer saw came from the shell's rail, so the prop appeared to work right up until someone passed a different value. It is wired now; the default is unset, because a default describing another component's rail was indistinguishable from one that applied. Inside the shell the rail still wins — set `--sidebar-width` on the shell to move the wrapper and its contents together.
- **`arc-sidebar.collapsed`** was documented as an icon-only mode and implemented as `width: 0`. The behaviour is right and the description was not; the JSDoc now says what it does and points at `arc-rail`, which is the icon-rail component.
- **`arc-page-header` reserved about 48px** below itself for three slots whether or not anything was in them. The wrappers still render — a slot removed from the shadow tree can never be filled again — and only the margins drop. Whitespace between tags does not count as content.
- **`arc-inline-edit` could not be focused from outside.** No `delegatesFocus`, everything focusable in the shadow root, so `el.focus()` did nothing at all, silently; it cost the reporter a "Rename" menu item that appeared dead. `focus()` now lands on whichever element is the control — the field while editing, the display row otherwise. `edit()` remains the way into editing.

### Toasts Can Be Driven Without A Reference

`arc-toast` is method-driven, and its document-level `arc-toast` event covered only `show()`. A consumer whose framework wrapper exposes no element handle could therefore raise a toast and do nothing else with it — `show()` returns the id the other methods need, and the return value of a method you did not call goes nowhere.

The route is complete: **`arc-toast-dismiss`, `arc-toast-update`, `arc-toast-complete` and `arc-toast-clear`**, beside the `arc-toast` that already existed. Pass `detail.id` on the way in to name the toast yourself, so the caller holds the id without needing the return value.

```js
document.dispatchEvent(new CustomEvent('arc-toast', {
  detail: { id: 'upload', message: 'Uploading', progress: 0 },
}));
document.dispatchEvent(new CustomEvent('arc-toast-complete', { detail: { id: 'upload' } }));
```

### Dev Warnings Say What You Are Looking At

Three v4 renames fail silently by construction: content with an unrecognised `slot=` is not rendered, an ignored `closable` just leaves the close affordance absent, and an unknown enum is **coerced to the declared default** rather than ignored — so `arc-confirm variant="danger"` renders a destructive dialog as an ordinary one.

`@arclux/arc-ui/dev` caught all three for the reporter, and also four `<Alert variant="danger">` in their own code that had never matched a real variant and had been rendering as neutral `info` notices since they were written. The enum warning now names the destination as well as the expectation — *`"danger" is not a valid variant — expected info | tip | success | warning | error; rendering as "info"`* — and the fallback is recorded per attribute in `custom-elements.json` and `dev-schema.js`, so a codemod can be written against the coercion rather than against a list of renames. MIGRATION.md opens with those three and the one import that finds them.

### Seven Components' Console Noise, From One Line

The report named three components logging Lit's `change-in-update` warning and made the right observation about them: *"it is now five components rather than one, which reads less like a sanctioned exception and more like a pattern."*

It was seven, and it was one line. `hydrateSlots()` — the helper that delivers the `slotchange` declarative shadow DOM eats — was called from `firstUpdated`, which runs *inside* the update, so every handler it reaches was writing state after the update completed. The dispatch is queued out of the cycle now, and four components that also carried a direct read from before the helper existed have lost the duplicate. `arc-app-shell`'s came from somewhere else and moved too.

`arc-icon` still warns and should: its registry lookup is genuinely async. That is the sanctioned exception, and it is legible as one now instead of being one of seven.

### Wrappers: Bindings, Handles, And 140 Dead Imports

Two of the eleven findings were the generator's rather than ours, and `@arclux/prism` 3.1.x took both.

- **Two-way binding is derived from behaviour, not from a prop's name.** A component that assigns to its own prop outside the constructor *and* announces it with an event is bound. Eight props gain one: `AppShell.sidebarOpen`, `Tabs.selected`, `Pagination.current`, `StepperNav.active`, `ScrollSpy.active`, `ThemeToggle.theme`, `ImageCompare.position`, `Waveform.position`.
- **Every component with public methods now exposes an element handle** in all five generated packages — `element()` in Svelte, `defineExpose` in Vue, a public getter in Angular, a forwarded ref in Solid and Preact. React already forwarded refs.
- **140 wrappers lose a dead type import** — an unused `Snippet` in 70 Svelte wrappers and an unused `type JSX` in 70 Solid ones, on every `@slot none` component. Both packages ship source, so it was the consumer's compiler that read them: with `noUnusedLocals` on, an error inside a file they never wrote.

### One Thing That Can Stop Compiling

**`Checkbox.value` is no longer two-way in the Svelte and Vue wrappers.** `arc-checkbox` announces `detail: { value: this.checked, checked: this.checked }` while declaring `value` as the string a form submits, so the old name-based rule mirrored the checked *flag* onto it — writing a boolean into a string prop. `bind:value` and `v-model:value` on a checkbox will stop compiling. `checked` is bound and is what that code meant.

Also worth knowing before upgrading: `arc-sidebar.width` now applies (default unset rather than `'280px'`), a slotted `arc-top-bar` inside `arc-app-shell` becomes `fixed` whether or not you set it, and `arc-page-header` no longer reserves space for empty slots — the last two are the fixes above, and both change layout by design.

### What The Batch Says About The Tests

The suite was not padded. The file that should have caught the dropdown panel is twenty lines of careful reasoning about `min-width` that even warns *"an empty panel would sit at min-width and pass the width assertions"* — and every assertion in it runs through a helper called `openMenubar`. The `min-width: 200px` it so carefully defends is the exact declaration that put 200px of panel off the page.

That test is not lazy. It is **framed**: it asserts something real, in a situation the consumer is never in. Four frames account for the whole batch — components mounted only in the state they are for, only alone, only with empty fixtures, and only measured against themselves. Two new files close the ones that can be closed: documented compositions mounted as compositions, and every overlay mounted closed and measured against the document.

The suite is at 4,733 tests. The six that matter were each watched failing against the unfixed source first, which is the only reason their passing means anything.
